# ai-stack/router/

## What it does

The decision layer that labels every request coming into the Navigator
assistant as either `local` or `cloud`, based on the hardware tier and model
readiness reported by `local-runtime/`, the user's preference
(privacy/cost/speed/balanced), and a rough estimate of the request's
complexity. If the decision is `local` it **really invokes** `local-runtime/`,
and if `cloud` it really invokes `cloud-bridge/` (see the integration
sections below). It is intended to be the central point where the assistant
panel (`shell/`) and `mcp-tools/` come together.

`router` does not call `hardware-probe` separately — `local-runtime`'s
report already contains the `hardware_tier`, `model_ready` and
`ollama_available` fields, so a
single subprocess hop is enough (see `router/status.py`).

**Both paths are now real end to end on this machine**: simple requests are
genuinely generated by local Ollama (`llama3.2:3b`); complex requests fall
through to `cloud-bridge` (since tier="low" counts as low capacity).

## Usage

No external dependencies, only Python 3.11+ (stdlib). It must sit next to
`local-runtime` and `cloud-bridge` (as sibling directories).

```sh
cd ai-stack/router
python3 -m router --prompt "Hello, who are you?" --pretty
python3 -m router --prompt "..." --prefer privacy   # balanced|privacy|cost|speed
python3 -m router --prompt "..." --decide-only      # decision only, DOES NOT EXECUTE (see below)
```

**`--decide-only`** (added in Phase 4 for `ai-stack/assistant`): returns only
the routing decision (`complexity`/`hardware_tier`/`model_ready`/`route`/
`reasoning`) and DOES NOT RUN `local-runtime` or `cloud-bridge`. It is for
callers such as `assistant` that want to build their own generation flow
(e.g. a tool-use loop) — having the router make its own tool-less
`generate()` call and then throwing the result away would be both wasteful
and an unnecessary real API call.

Tests:

```sh
cd ai-stack/router
python3 -m unittest discover -v -s tests
```

## Example output — the cloud path

A complex (long) request — because tier="low" counts as low capacity, it
falls through to `cloud` even when `model_ready: true`. When the Claude API
credential is sourced via `cloud-bridge/.env.local` (see
`ai-stack/cloud-bridge/README.md`) a real response comes back; when it is
not sourced (the default, including CI) a graceful "unavailable":

```json
{
  "schema_version": "0.1",
  "complexity": "complex",
  "hardware_tier": "low",
  "model_ready": true,
  "route": "cloud",
  "cloud_bridge": {
    "status": "ok",
    "model": "claude-opus-4-8",
    "content": "Ankara"
  }
}
```

## Decision logic (draft, `router/decision.py`)

1. If `model_ready == false` (Ollama is down or the model has not been
   pulled): **always `cloud`**, whatever the preference.
2. `privacy` or `cost` preference: **always `local`** if the model is ready.
3. `speed` preference: complex request + low tier (`minimal`/`low`) →
   `cloud`; otherwise `local` (no network latency).
4. `balanced` (default): complex request + low tier → `cloud`; otherwise
   `local`.

The complexity estimate (`estimate_complexity`) is a very rough heuristic
for now: word count > 40, multi-line, OR `mentions_tool_keywords()` (added
in Phase 4) detecting keywords relating to hardware, the filesystem or
windows → "complex". That last part solves a problem verified in real
testing in `ai-stack/assistant`: short requests that nonetheless need tools
("how many CPU cores are there?") used to fall through to local because only
the word count was considered, and because the small local model on a low
tier has poor tool-use reliability (see `ai-stack/assistant/README.md`,
"Local tool-use") it sometimes produced a wrong answer. Now such requests
count as "complex" too and are routed to the cloud (on a low tier) —
verified in real testing (on this machine tier="low", and "How many CPU
cores does this machine have?" now automatically gets `route: "cloud"`).
This is not real intent classification but a rough keyword scan; all
thresholds are still a draft.

## local-runtime integration

When the `route: "local"` decision is made, `router/local.py` runs
`python3 -m local_runtime --prompt "<request>"` as a subprocess and adds the
result to the report's `local_runtime` field. Possible states:

- `{"status": "ok", "content": "..."}` — the real request succeeded
  (verified on this machine)
- `{"status": "unavailable", "reason": "ollama_not_running"}` — Ollama is down
- `{"status": "unavailable", "reason": "model_not_installed"}` — Ollama is up
  but the recommended model has not been pulled
- `{"status": "unavailable", "reason": "no_local_model_recommended"}` — tier
  is "minimal", no local model is recommended
- `{"status": "error", "error": "..."}` — a network/request error (e.g. a
  timeout)

**Known limitation:** the default timeout of `OllamaClient.generate()` is
300 seconds — on the first attempt a real generation call timed out with the
5-second default (the model is being loaded into memory and inference runs
on CPU); this was caught and fixed on the real machine.

## cloud-bridge integration

When the `route: "cloud"` decision is made, `router/cloud.py` runs
`python3 -m cloud_bridge --prompt "<request>"` as a subprocess and adds the
result to the report's `cloud_bridge` field. Three possible states:

- No credentials: `{"status": "unavailable", "reason": "credentials_not_configured"}`
- A real request succeeds: `{"status": "ok", "content": "..."}`
- A network/request error: `{"status": "error", "error": "..."}`

Each decision invokes only its own target: `cloud-bridge` is not called when
`local`, and `local-runtime` is not called when `cloud` (verified by tests).

## Out of scope — not done yet

- Tool calls arriving via `mcp-tools/` use the `route_request` tool (see
  `ai-stack/mcp-tools`) — this now automatically inherits both the `local`
  and the `cloud` integration.
- The cloud credential exists only on this development machine
  (`cloud-bridge/.env.local`, gitignored) — it is not defined as a secret in
  CI, so the cloud path still reports "unavailable" on GitHub Actions.

## Status

Phase 2 — the decision/orchestration layer, the **local-runtime
integration** and the **cloud-bridge integration** are complete
(`decision.py`, `status.py`, `local.py`, `cloud.py`, and the
`python3 -m router` CLI). The `--decide-only` flag AND
`mentions_tool_keywords()` (the "might this need tools?" signal in the
complexity heuristic) were added in Phase 4 (see above). 38 tests pass — one
is a real local Ollama generation (`route: "local"` end to end, producing
real text), one is credential-less cloud routing (`route: "cloud"`, a
graceful "unavailable" — always works, including in CI), one is a real cloud
generation with credentials (a real Claude API response when `.env.local` is
sourced — automatically skipped when there are no credentials), one verifies
that a short but tool-requiring request now genuinely gets an automatic
`route: "cloud"` on this machine (tier="low"), three verify
`--decide-only`, and one verifies that a Turkish prompt reaches the same
routing decision as its English equivalent. **`router` is now a fully real,
working system on this machine** — no path is a mock or placeholder, and
both the local and the cloud end genuinely generate.

**A note on `TOOL_KEYWORDS`:** it deliberately carries both English and
Turkish keywords. The repository's documentation and code are English, but
the assistant replies in whatever language the user writes in (see
`SYSTEM_PROMPT` in `ai-stack/assistant`), so a Turkish request must be
routed exactly like its English equivalent. Adding a language here means
*adding* its keywords, never replacing the existing ones — and
`test_turkish_prompt_reaches_the_same_decision` is what catches a
replacement.
